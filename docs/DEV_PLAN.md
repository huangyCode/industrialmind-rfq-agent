## 1. 拆分思路

### 1.1 按什么原则拆

| 原则 | 做法 | 原因 |
|---|---|---|
| **先定接口，再并行** | 主控先写 `CONTRACTS.md`：每个模块的函数签名、输入输出模型、负责哪些文件 | 并行开发最大的风险是接口对不上；接口定死后，各 agent 可以各写各的，最后拼装不返工 |
| **按依赖关系分阶段** | 互不依赖的模块放同一阶段并行；有依赖的放到后一阶段 | 阶段内部并行，阶段之间串行，避免 agent 等待或读到写了一半的代码 |
| **确定性模块不等模型** | 规则、工艺、成本、置信度都用手写的测试输入开发 | 模型下载、模型效果都有不确定性，不能让它卡住主体开发 |
| **依赖模型的工作单独隔离** | 模型层代码（阶段 1）与真实录制（阶段 2）分开 | 代码可以先用假 provider 测完；录制只在模型就绪后做 |
| **集成只交给一个 agent** | LangGraph 编排 + CLI + 报价输出由同一个 agent 完成 | 集成需要看全局，拆给多人会出现各自理解不一致 |
| **文件所有权唯一** | 每个文件只有一个 agent 能写；共享文件（config / models / db / repositories）只在指定阶段由指定 agent 改 | 防止并行写冲突 |
| **agent 不提交代码** | 每阶段结束由主控跑全量测试 + lint，通过后统一 commit | 每个 commit 都是可运行状态，出问题容易回退 |

### 1.2 为什么是这 10 个 agent

- **阶段 1 的 5 个 agent 之间零依赖**：样例数据、知识库+规则、模型层、工艺+BOM、成本+置信度，它们只依赖已经完成的 models 和主数据。
- **历史件 + 相似件放阶段 2**：历史件要生成"与演示样例相近的锚点件"（依赖样例图纸的参数），还要用成本引擎算历史成本（依赖 costing）；相似件检索需要历史件数据才能测试。所以这两件事合在一个 agent，放在阶段 2。
- **抽取录制放阶段 2**：需要样例 PDF（samples）+ 模型层（llm）+ 视觉模型下载完成。
- **编排放阶段 3**：需要所有模块。
- **UI 和评测放阶段 4 并行**：都只依赖编排层暴露的接口，彼此不写同一个文件。
- **README 和最终检查由主控做**：README 要讲业务和架构决策，需要全局视角；推送公开仓库前的安全检查（密钥、公司信息）必须主控亲自确认。

## 5. 风险与预案

| 风险 | 预案 |
|---|---|
| 7B 视觉模型读图准确率低 | 图纸按"清晰优先"绘制；评测如实报告；下游的校验和置信度分流会把抽错的字段转人工，这正是演示人工审核价值的机会；模型层支持切换云端模型做对比 |
| Ollama 对"图片 + 结构化输出"支持不稳定 | llm agent 同时实现 JSON Schema 约束和"提示词要求 JSON + Pydantic 校验重试"两条路 |
| 合成数据让分流结果和预期不一致 | eval agent 可调阈值/系数，但必须在报告里写明改了什么、为什么 |
| 并行 agent 改到同一文件 | 按 CONTRACTS.md 的文件所有权；主控每阶段检查 `git status` 是否有越界改动 |
| 今天做不完 | 阶段 3 结束即为可提交版本；阶段 4 做多少算多少，没做的在 README 中如实说明 |
